# Jev 式决策协作实验：前两轮对照报告

更新：2026-09-29 23:28 Asia/Shanghai。负责人：lqj。

## 研究目的与结论

**验证合理采用“决策模型选择动作与目标、大模型承担必要生成和辅助”的协作方式，能否加快 Agent 完成任务，同时保持相近的任务通过率。** 本实验用 `cklxx/laya-browser` v19s 承担 Jev 式决策角色，与用户指定的同一个 Qwen2.5-72B 协作；不是 TypeSafe Jev 原模型的实测成绩。

按 lqj 确认，本报告只分析受控重跑的**前两轮：16 个任务 × 2 组 × 2 次，共 64 次尝试、32 个配对**。每轮全部任务纳入，包括失败；以完整任务覆盖限定范围，不按分数选题，不混入其他运行的数据。原始记录不改写。

主要发现：

- **通过率未观察到下降**：纯 Qwen 为 **24/32（75%）**，Laya+Qwen 为 **26/32（81.25%）**；两轮分别都是 12/16 对 13/16。
- **大模型请求明显减少**：Qwen 实际 HTTP 请求 **169 对 21，减少约 87.6%**，但 B 另有 **179 次 Laya 请求**，不能表述为总模型调用减少 87.6%。
- **观察到成功任务提速**：双方成功的 22 对速度比为 **1.857 倍**；其中双方均无 Qwen HTTP 失败的 20 对约 **1.431 倍，耗时减少 30.1%**。后者是检查限流影响的事后敏感性分析，不代表所有任务。

这是支持研究方向的初步证据，**不是统计质量等价证明，也不能据此认定 Laya 的通用能力强于 Qwen**。

## Jev 式分工在本实验中如何实现

这里的“Jev 式”指公开浏览器实现中的选择与生成分工，实际选择模型是 Laya。它直接决定如何推进任务，不只是判断“要不要再问大模型”。

| 环节 | A：纯 Qwen | B：Laya+Qwen |
| --- | --- | --- |
| 读取网页状态、提供可操作元素与候选 | 浏览器框架 | 同一浏览器框架 |
| 选择动作和目标 | Qwen 根据当前状态输出操作及目标索引 | Laya 从当前候选中选择操作及目标，如点击、填写、下拉选择、滚动、等待 |
| 填写文本 | Qwen 在同一次决策响应中给出文本，不人为拆成多次请求 | Laya 先选填写动作和字段，Qwen 再生成字段文本 |
| 下拉选项 | Qwen 在决策响应中直接选具体选项 | 保留作者 helper：Laya 选择下拉动作/目标，Qwen 可辅助确定具体选项值 |
| 结束或无法推进 | Qwen 可选择 DONE / BLOCKED | Laya 可选择 DONE / BLOCKED |
| 实际工具执行 | 框架校验并执行 | 框架校验并执行，Laya 不直接操作浏览器 |
| 最终成功判定 | 独立任务验收器 | 同一独立任务验收器，不把模型的 DONE 当成功证明 |

两组均保留作者共有的执行保护；B 保留作者包装器的输入压缩、截断和候选分块。本轮未开启额外规划、大模型升级代选或 LLM 完成检查。不能把作者方案简化为“Qwen 绝不参与选择”：**下拉值辅助确实启用，并单独计数**。

分工依据为固定作者发布包中的 [laya_browser.py](https://huggingface.co/cklxx/laya-browser/blob/645cf366a2ae35f1086e8c20eff48f909bb49206/code/apps/laya_browser.py)、[引擎补丁](https://huggingface.co/cklxx/laya-browser/blob/645cf366a2ae35f1086e8c20eff48f909bb49206/code/jev-ultrafast.patch)，以及本地已记录的请求用途；A 的实现见 [author_control.py](../../scripts/benchmarks/jev_browser/author_control.py)。

## 实验条件

| 项目 | 本次条件 |
| --- | --- |
| 任务来源 | 浏览器权重作者发布的 Suite A 16 题，同任务、同引擎；纯 Qwen 组是我们补充的本地对照，不是作者已发布的配对成绩 |
| 大模型 | 两组均为 SiliconFlow `Qwen/Qwen2.5-72B-Instruct`，不是作者本地 Qwen3-8B |
| 决策模型 | `cklxx/laya-browser` v19s，固定快照 `645cf366a2ae35f1086e8c20eff48f909bb49206` |
| 本地环境 | Windows、RTX 5070 Ti 16 GiB、BF16、`fast=False`；Python 3.13.9、torch 2.11.0+cu128、Laya 0.3.21、transformers 5.17.0、browser-harness 0.1.13 |
| 公共生成参数 | `temperature=0`、`top_p=1`、`max_tokens=1024`、JSON 输出；A 合并决策与必要文本，B 按作者 helper 调用 |
| 网络与运行顺序 | 浏览器和 Qwen 均显式使用同一本地代理，Laya/CDP 直连；按题与轮次交替 A/B 先后，每次独立浏览器上下文，工程测试不与计时并行 |
| 执行约束 | 相同 20 步上限、180 秒协作式边界时限；共同空值修复，不增加任务专用规则代选 |
| 限流处理 | 两组最多三次 HTTP 尝试，429 等待 30/60 秒并尊重有界 Retry-After；等待计入墙钟，不删除失败 |
| 计时边界 | 单次任务启动至验收结束的墙钟，含浏览器工作、模型、网络、工具、等待及重试；模型加载和预热不纳入任务时间 |

这是当前部署下两种完整方案的比较，**不是最终输入完全相同的模型参数消融**。远端 Qwen 的硬件、缓存不可控；B 的作者预处理属于方案的一部分。详细版本依据见[作者复现报告](laya-browser-author-reproduction-20260929.md)。

## 结论边界

- **质量差异只有每轮净多通过 1/16 个任务**。A 在 wiki-search 的候选协议错误有原始响应证据；hn-past 涉及浏览器 IPC 与限流等待，不能把这两次失败都说成决策能力不足。B 也在 books-open-book 两次失败。当前纯 Qwen 接入不代表其最佳可达表现。
- 两轮 10 次 429 均明确返回 `50602 / TPM limit reached`，后续重试均取得 HTTP 200，但等待仍可能导致任务超时。速度同时报告含等待和无 HTTP 失败的成功配对，不将全部等待差异解释为本地模型推理优势。
- 180 秒只在操作边界检查，不能硬中断正在进行的调用，因此有 192.997 秒的失败记录。失败尝试的短耗时不等于有效提速。
- 只有 27/32 对初始观测散列一致，不能宣称网页初态完全相同。原航班题日期为 2026-09-28，运行日在 09-29，题目已过期但仍保留在分母。原验收部分依赖 URL/标题，故报告的是任务验收通过率，不是强语义准确率。
- 独立任务只有 16 个，重复两次不等于 32 个独立任务；未预先设定质量等价容忍度。不能由 75% 对 81.25% 宣布统计质量等价，也不能推广成“Jev 普遍优于 LLM”。

## 汇报口径

建议汇报：**“基于作者公开浏览器任务的完整两轮对照，Laya+Qwen 为 81.25%，纯 Qwen 为 75%；未遇到 HTTP 失败的共同成功配对约快 1.43 倍，全量 Qwen 请求减少约 87.6%。这支持协作方案在当前部署下的应用价值，但不证明统计质量等价。”**

决策模型分担的是动作与目标选择，Qwen 仍负责必要的字段文本和作者下拉值辅助。下一步由非作者核对这份两轮报告及逐次证据；本次只整理报告，不追加模型调用或改动实验数据。
