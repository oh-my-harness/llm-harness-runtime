# 实验方案：大模型生成与 Laya 决策的分工

更新：2026-09-29 10:17 Asia/Shanghai。负责人：lqj。
状态：lqj 已明确选择 Laya 作为决策模型，取代上一版的原版 Jev 优先建议；具体 checkpoint 与实施条件待确认，尚未实现或运行本方案，没有有效实验结果。

## 1. 唯一研究目标

**验证“大模型负责必要的生成，决策模型负责根据当前状态从已有候选中判断与选择”的协作方案，相比大模型同时承担生成与决策，是否降低端到端耗时，以及任务完成质量如何变化。**

本实验不是“小型生成式 LLM 全面替换大模型”，也不是“规则或硬编码计划替模型决策”。本次“小模型”明确指 Laya 决策组件，不把普通 LLM 的 JSON 输出当作 Laya，也不把 Laya 当作 Jev 原版。

目标不得由执行者自行改写。遇到模型不可用、接口不匹配或任务不适合时，记录问题并向 lqj 确认，不得换一个容易实现的实验后沿用本目标的名称。

## 2. 概念与职责边界

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| 大模型 L | 生成计划、代码、补丁、无法从已有状态直接取得的参数；必要时重规划 | 在实验组中包办本应由决策模型承担的选择 |
| 决策模型 D（Laya） | 读取当前可见状态、问题与已有候选，输出选项；接口支持时记录概率或评分 | 自由生成代码、工具参数或新的候选内容；亲自执行工具 |
| 框架 | 保存状态、整理观测、构造合法候选、校验参数、执行工具、记录过程 | 根据题号、隐藏答案或专用解题规则替模型选出正确动作 |
| 独立验收器 | 检查最终产物和可执行测试，判定任务是否成功 | 将隐藏答案或评分结果反馈给运行中的模型 |

本实验使用 Laya 对状态与已有候选进行判断，不要求它生成代码或工具参数。输出合法不代表选择一定正确；本文的两组对照是我们的实验设计，不是 Laya 项目已验证的协作效果。

### 2.1 已确认的选型：使用 Laya

核查日期：2026-09-29。lqj 基于 Jev 原版闭源的考虑，明确要求直接使用 Laya 替代。本次模型选择已获确认，研究目标仍是生成与决策分工的速度及质量，不改成 Laya 与 Jev 的模型排名比较。

| 对象 | 当前决定 | 对本研究的意义与限制 |
| --- | --- | --- |
| Laya | 已选为 B 组决策模型 D；开放代码及模型权重，使用编码器和决策头评分，支持 Choice、Score、Noul | 采用可锁定权重的本地部署路线；具体 checkpoint、部署配置及任务质量尚未验证 |
| 原版 Jev | 不用于本次实验，不申请或等待其 API 访问权限 | 仅作为概念背景；不设 Jev 实验组，不将 Laya 结果署名为 Jev 结果 |

Laya 的英语基础版 `convaiinnovations/laya` 为 421M 参数、默认 512 token 上下文；多语言版 `convaiinnovations/laya-multilingual` 为 322M、默认 1024；`convaiinnovations/laya-typed-decisions` 为 421M、默认 1024。源码的单窗口推理会截断过长状态，多窗口方法则改变推理与计时口径。实施前必须锁定其中一个 checkpoint、代码与权重版本、输入语言和预算，不能让 Router 自动切换模型。输入裁剪须对两组一致，并记录截断情况；不能因 Laya 上下文较短而悄悄省掉必要信息。来源：[Laya 项目说明](https://github.com/NandhaKishorM/laya/blob/9d955671415fc19f069b9cc998928075c1f255ec/README.md)、[已核查的推理源码](https://github.com/NandhaKishorM/laya/blob/9d955671415fc19f069b9cc998928075c1f255ec/laya/agent.py)。

尤其不能因为名称含有 typed-decisions 就默认采用该微调版：其训练覆盖四类合成业务流程，并非通用代码修改任务；模型卡明确提示领域外效果与置信度校准问题。卡中与 Jev 的比较并非作者在相同条件下重新实测，不能据此断言 Laya 优于 Jev。来源：[Laya Typed-Decisions 模型卡](https://huggingface.co/convaiinnovations/laya-typed-decisions/blob/main/README.md)。

**当前决定：D = Laya，不再将 Laya 视为备选。** 不因模型选择已确认就自动确定 checkpoint 或启动实验；遇到本地部署不可用或质量不符合预期时如实记录，不静默切回 Jev、普通小型 LLM 或规则模拟。

### 2.2 Laya 决策预检与端到端评测

单独测 Laya 的 Choice 只能回答局部选择能力与耗时，不能直接证明协作系统提速。建议在获准后按以下顺序验证，两阶段不能互相替代：

1. **决策预检，属于试跑：** 从拟定任务的开发样例中冻结可见状态、问题与候选，让 L 与 Laya 分别选择。独立标注可接受选项，记录选择准确率、无效响应与错误、调用方完整耗时及重试次数。允许多种正确选择，不以 L 的答案当作真值。样例数量、语言与标注规则须先确认；全部预检结果保留，不能只挑 Laya 擅长的题进入正式任务。
2. **端到端正式对照：** 仍按第 3 至 7 节比较 A 与 B，在各自轨迹中真实生成和执行工具，回答完整任务是否更快、任务准确率如何变化。预检的状态和候选只用于隔离决策能力，不能免费复用于正式运行，也不能把预检准确率当作任务完成率。

部署后须验证实际加载的 checkpoint、权重 revision、设备和输出结构；固定推理后端、精度、上下文及候选预算。确认计时路径确实执行模型推理，不能把 Laya CLI 的仅路由模式误计为决策模型耗时。本轮尚未下载或加载权重，没有本机性能数据。

## 3. 两组对照

只设置以下两组，不擅自加入规则辅助组、全小模型组或 Jev 组；D 已确认为 Laya，具体 checkpoint 和配置须在实施前冻结：

| 条件 | A：大模型生成与决策 | B：大模型生成 + Laya 选择 |
| --- | --- | --- |
| 必要的生成与重规划 | 大模型 L | 同一个大模型 L |
| 已有候选中的选择 | 大模型 L | Laya（D） |
| 状态与候选构造、工具执行 | 相同框架 | 相同框架 |
| 任务、初始环境与验收 | 相同 | 相同 |

两组都使用明确的决策接口：同一状态下提供同样的候选及语义，A 由 L 返回选项，B 由 D 返回选项；生成接口另行调用 L。这样对照的是决策组件替换，而不是同时改变模型、工作流和工具能力。

A 只需返回候选 ID，不为模仿 Laya 的接口强迫 L 额外生成解释或整份概率分布；B 可记录接口原生返回的概率，但不默认据此触发回退。调用批量大小与每次包含的决策数量须提前冻结，不能把多问题的一次调用与另一组的多次调用混为一次决策的提速。

这不是将任意现成 ReAct 产品直接与新系统比较。结论只适用于本方案定义的共同工作流，不外推为对所有 Agent 框架的提速。

两组独立执行。选择不同会导致后续状态与调用次数不同，应完整记录，不强行保持轨迹一致，也不把 A 组生成的计划或补丁免费提供给 B 组。

## 4. 候选与工具参数从哪里来

以下为待确认的实现约束，不代表已有实现：

- 框架可以从真实可见状态列出合法操作，例如已发现文件的读取动作、配置中已有的测试命令、已有补丁的应用动作。
- 需要开放式生成的内容由 L 产生，例如新补丁、计划或新参数；相应调用必须计入该组耗时与调用次数。
- 每个候选绑定动作、已有参数或产物引用、来源和适用状态。D 只选择候选 ID，框架按绑定执行，不能在模型选完以后偷偷补上正确答案。
- 缺少参数或有效候选时，必须有明确的“请求生成/重新规划”或“无法继续”路径，不能要求 D 编造参数。两组遵循相同协议。
- 同一套候选构造代码用于两组；候选数量、顺序、描述、状态截断、失效条件与刷新策略在运行前冻结。
- 状态更新、路径与权限检查等确定性工作可以由框架完成，但不能为实验组独有地加入解题逻辑。验收答案、隐藏测试和任务专用正确动作不能进入候选构造。

示意流程：L 生成补丁 -> 框架保存产物与可执行候选 -> L（A 组）或 D（B 组）选择下一步 -> 框架执行工具并更新状态 -> 再次判断是否需要生成、继续操作或结束。具体任务流程与调用位置须在实现前确认。

**加速是待检验假设，不是保证。** 不预设每一步都先请求 L 生成候选，再额外调用 D。若实际需要这样做，相关成本必须全部计入，系统可能更慢。也不能为了减少 L 调用而让 D 或规则承担原本需要生成的工作。

## 5. 任务与公平性

- 任务须同时存在真实的生成需求和有意义的后续选择，不能仅用分类题代替整个 Agent 任务，也不能只测生成任务。
- 采用独立验收的任务，优先包含代码或文件修改及可执行测试；覆盖正常执行、信息不足、工具失败后的恢复。具体任务及数量待 lqj 确认。
- 试跑与正式评测任务分离。正式任务、提示词、模型版本和验收规则在看结果前冻结，禁止看到失败后修改答案或删题。
- 同题同重复轮次配对，在相同初始工作区独立运行；两组先后顺序均衡，具体随机种子与重复次数提前固定。重复运行不算新的独立任务。
- 两组使用相同 L 的接口、版本、生成提示词、采样配置、上下文与输出预算；D 的配置另行完整记录。
- 决策问题、候选和状态的语义一致；不同接口必要的序列化差异如实记录，不能给其中一组额外信息。不同轨迹只使用各自实际获得的观测。
- 工具集、任务级时间预算、动作预算、超时、重试、故障注入规则、缓存政策与预热口径一致并冻结。SDK 自动重试也必须显式配置与计数。
- 不假定概率可直接作为可靠置信度。若引入低置信度回退到 L，须事先确认规则、独立校准并对两组明确适用方式，禁止看正式结果后调阈值。

## 6. 必须记录的量化数据

| 指标 | 口径 |
| --- | --- |
| 任务准确率 | 独立验收通过次数 / 全部正式任务尝试；失败、超时、预算耗尽均计入分母 |
| 端到端耗时 | 工作区就绪且任务开始后，到最终验收结束；包含首次规划、候选生成、决策、工具、重规划、重试与恢复，不只计 D 的响应时间 |
| 耗时分布 | 两组全部尝试的均值、中位数、p95；另列成功与失败耗时，不能把提前放弃算作有效提速 |
| 成功配对加速比 | 双方均成功配对中，A 的平均耗时 / B 的平均耗时；同时报告配对数量，不能只给筛选后的速度而隐藏失败 |
| 模型调用 | 按 L-生成、L-决策、D-决策、回退用途分开记实际调用数（远程请求或本地推理）、决策问题数、逐次及累计耗时、输入输出 token、错误与重试；本地批量大小及实际前向次数另记，一次批量调用不等于一次决策，回退用途另标，不能重复加总 |
| 工具与框架 | 工具逐次及累计耗时、次数、失败；候选构造、状态整理与验收开销单列，避免漏算 |
| 分工是否成立 | B 中实际由 D 承担的决策次数、L 请求总数及生成次数变化、重规划和回退次数 |
| 质量细分 | 每题结果、两组独有失败、错误恢复、破坏既有内容、提前结束；模型说完成不等于验收通过 |

每个记录须能关联运行、任务、重复轮次、实验组、请求用途和产物。保留脱敏后的状态、候选及来源、选择和工具结果以供核对；不得记录密钥。

模型加载、预热、工作区准备、清理与结果落盘另计，并给出整场运行总时间。若任务中触发加载或联网等待，必须留在端到端耗时内。阶段并行时同时记录实际墙钟时间与阶段耗时，不能简单相加后当作总耗时。

记录操作系统、CPU/GPU/内存、推理服务及模型版本、精度、上下文设置、思考配置、网络端点类别、并发、运行顺序和代码/任务集版本。服务端未知条件标为未知；部署差异不能全部归因于模型架构。

## 7. 如何解释结果

主要回答两个问题：B 是否更快；B 相对 A 的准确率变化是多少。先报告全部任务的质量与耗时，再报告双方成功配对的加速。

- 准确率差值按 B 减 A 报告，并报告不确定性；重复数据以独立任务为单位分组分析，不能把同题多次运行当作独立样本放大证据。
- “质量可接受的下降幅度”、正式任务量、重复次数与统计方法必须在正式运行前确认。未预设质量容忍度或证据不足时，只描述观测差异，不宣称质量等价。
- 即使 D 单次判断更快，若额外生成或恢复使任务整体变慢，也须报告协作方案未提速。
- 不预设加速倍数、目标延迟或成功结论；失败和负结果同样保留。
- 结果明确署名为“大模型生成 + Laya 决策”协作实验，并注明 checkpoint；只能支持本配置下的分工效果，不能作为 Jev 原版结果或所有决策模型均有效的证据。
