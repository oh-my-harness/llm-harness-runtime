# 实验方案：大模型生成与 Laya 决策的分工

更新：2026-09-29 13:45 Asia/Shanghai。负责人：lqj。
状态：已实现并离线验证公开 Jev Agent 的直接动作/目标选择分工；35 项测试通过，其中 9 项使用真实隔离 Chromium。已部署 Laya 的 512/192 输入预算检查发现指令裁剪，暂不进入真实模型 A/B。旧 AppWorld 路由式接法已撤下。无新付费调用，无“更快且准确度相近”的结论。

## 1. 唯一研究目标

**验证“大模型负责必要的生成，决策模型负责根据当前状态从已有候选中判断与选择”的协作方案，相比大模型同时承担生成与决策，是否降低端到端耗时，以及任务完成质量如何变化。**

本实验不是“小型生成式 LLM 全面替换大模型”，也不是“规则或硬编码计划替模型决策”。本次“小模型”明确指 Laya 决策组件，不把普通 LLM 的 JSON 输出当作 Laya，也不把 Laya 当作 Jev 原版。

目标不得由执行者自行改写。遇到模型不可用、接口不匹配或任务不适合时，记录问题并向 lqj 确认，不得换一个容易实现的实验后沿用本目标的名称。

## 2. 概念与职责边界

以 [browser-use/jev-ultrafast 固定源码](https://github.com/browser-use/jev-ultrafast/tree/1231850a0bf1a0c0341fe408ef1668dbbfdfac46) 为分工依据。这是调用 Jev 的公开 Agent，不是 Jev 模型权重开源；本实验只用 Laya 替代其决策组件，不能把结果归属于 Jev 本体。

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| 大模型 L（B 组） | 仅在已选中 `TYPE_TEXT` 及目标输入框后，生成所需文本 | 再次选择业务动作、目标或整套浏览器操作；生成可执行代码 |
| 决策模型 D（Laya） | 从观测得到的候选中直接选择操作及对应目标，例如点击哪个按钮、选择哪个原生下拉选项 | 只做“是否调用大模型”的路由；自由生成文本、选择器或代码 |
| 框架 | 观测并编号当前控件、记录状态、验证目标仍有效、执行已选动作、记录过程 | 用任务专用脚本或隐藏答案替模型选择正确操作 |
| 独立验收器 | 根据任务预先定义的最终页面/状态条件判定成功 | 相信模型的 DONE；向运行中的模型透露验收条件或评分结果 |

“直接选择动作与目标”是必要条件，不是措辞上的变化。B 中 Laya 选择 `CLICK` 后执行点击，不再请 Qwen 决定点哪里。框架执行工具，Laya 本身不执行工具。最终质量以完整任务独立验收为准，不以单步输出格式合法为准。

### 2.1 已确认的选型：使用 Laya

核查日期：2026-09-29。lqj 基于 Jev 原版闭源的考虑，明确要求直接使用 Laya 替代。本次模型选择已获确认，研究目标仍是生成与决策分工的速度及质量，不改成 Laya 与 Jev 的模型排名比较。

| 对象 | 当前决定 | 对本研究的意义与限制 |
| --- | --- | --- |
| Laya | 已选为 B 组决策模型 D；开放代码及模型权重，使用编码器和决策头评分，支持 Choice、Score、Noul | 英语基础版已完成 GPU 接入检查；正式任务适用性与任务质量尚未验证 |
| 原版 Jev | 不用于本次实验，不申请或等待其 API 访问权限 | 仅作为概念背景；不设 Jev 实验组，不将 Laya 结果署名为 Jev 结果 |

Laya 的英语基础版 `convaiinnovations/laya` 为 421M 参数、默认 512 token 上下文；多语言版 `convaiinnovations/laya-multilingual` 为 322M、默认 1024；`convaiinnovations/laya-typed-decisions` 为 421M、默认 1024。源码的单窗口推理会截断过长状态，多窗口方法则改变推理与计时口径。实施前必须锁定其中一个 checkpoint、代码与权重版本、输入语言和预算，不能让 Router 自动切换模型。两组具有相同的可见任务信息和工具权限；若 B 为适配 D 而额外压缩状态，必须记录信息损失及全部成本，不能为了迁就 Laya 而把正常大模型基线也强行压缩到 512 token。来源：[Laya 项目说明](https://github.com/NandhaKishorM/laya/blob/9d955671415fc19f069b9cc998928075c1f255ec/README.md)、[已核查的推理源码](https://github.com/NandhaKishorM/laya/blob/9d955671415fc19f069b9cc998928075c1f255ec/laya/agent.py)。

尤其不能因为名称含有 typed-decisions 就默认采用该微调版：其训练覆盖四类合成业务流程，并非通用代码修改任务；模型卡明确提示领域外效果与置信度校准问题。卡中与 Jev 的比较并非作者在相同条件下重新实测，不能据此断言 Laya 优于 Jev。来源：[Laya Typed-Decisions 模型卡](https://huggingface.co/convaiinnovations/laya-typed-decisions/blob/main/README.md)。

**当前决定：D = Laya，不再将 Laya 视为备选。** 英语基础版已用于部署检查，不代表其适合完整 Agent 状态，也不代表正式 checkpoint 已冻结。遇到本地部署不可用或质量不符合预期时如实记录，不静默切回 Jev、普通小型 LLM 或规则模拟。

### 2.2 接入检查不替代端到端评测

按 lqj 后续澄清，主线是完整 Agent 系统是否更快且保持相近任务准确度，不先另做一项分类排行榜研究：

1. **部署及接口冒烟检查：** 验证 Qwen 请求成功、Laya 加载固定权重且真实执行前向、设备与计时记录正确。短样例只检查接口及暴露明显风险，不宣称任务准确率，不据此计算系统加速比。
2. **端到端开发试跑及正式对照：** 按第 3 至 7 节比较 A 与 B，在各自轨迹中真实生成和执行工具，以独立验收判定完整任务是否完成。保留所有失败，不只挑 Laya 擅长的题进入正式测试；开发任务与正式任务分离。

部署后须验证实际加载的 checkpoint、权重 revision、设备和输出结构；固定推理后端、精度、上下文及候选预算。确认计时路径确实执行模型推理，不能把 Laya CLI 的仅路由模式误计为决策模型耗时。已完成的部署检查见第 8.3 节，不能作为研究结果。

## 3. 两组对照

只设置以下两组；L 固定为已获确认的硅基流动 `Qwen/Qwen2.5-72B-Instruct`，不新增规则组、小型生成模型组或原版 Jev 组。

| 条件 | A：正常 Qwen 浏览器 Agent | B：Laya 决策 + Qwen 文本生成 |
| --- | --- | --- |
| 操作和目标选择 | Qwen | Laya |
| TYPE_TEXT 的填写文本 | Qwen，可与选择合并在同一请求 | 同一个 Qwen，仅生成已选输入框的文本 |
| 状态、候选及执行器 | 同一套公开实现适配 | 同一套公开实现适配 |
| 任务、初始状态和独立验收 | 相同 | 相同 |

**A 一次请求可同时给出操作、目标及填写文本，不强制拆成“先选择、再生成”两次请求。** 纯选择步骤不要求 A 生成解释或概率分布。B 使用一次 Laya `predict` 提交操作及各类目标问题，只执行选中操作对应的目标；实际前向次数另计，不能假定一次 predict 等于一次前向。

两组共享可见信息、Qwen 模型及采样/输出预算。由于 A 允许联合输出、B 只请求文本，两者提示语结构不同，但任务信息和文本填写要求一致，完整请求均留痕。不同轨迹使用各自实际获得的观测；不共享对方生成内容，不强行令调用次数或路径相同。

这是本配置下的系统级比较，不是纯推理 kernel 速度比较；远程 Qwen 与本地 Laya 的部署差异必须披露。

## 4. 候选与工具参数从哪里来

已实现的协议对应上游 [model.py](https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/model.py) 和 [agent.py](https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/agent.py)：

1. 框架从真实 DOM 观测当前可见控件，生成编号元素表及支持的操作。无 LLM 候选生成，无预先写好的任务操作序列。
2. 操作为 `CLICK`、`TYPE_TEXT`、`SELECT`、`SCROLL_UP`、`SCROLL_DOWN`、`WAIT`、`DONE`、`BLOCKED`；仅提供当前支持的操作和对应目标。
3. 操作问题与 click/type/select 的目标问题共用同一观测，批量交给 Laya。未选中的目标头即使有输出，也无权触发执行。
4. 点击/滚动/等待直接执行；原生下拉选项来自观测到的 element/option 编号，框架不补答案。只有 `TYPE_TEXT` 才让 Qwen 返回单字段文本 JSON，拒绝附带动作或代码。
5. 执行前复核页面与目标有效性，检查遮挡。模型不能输出 CSS 选择器、坐标、Python、JavaScript 或 shell 指令。
6. 页面失效后重新观测与决策；只有文本生成器的完整输入完全相同时，才复用其尚未执行的文本。浏览器变更成功后先记日志，再观察结果，不自动重放不确定的变更。
7. `DONE` 只是结束信号；终末独立检查通过且未超时才算任务成功。

源码复用与必要适配逐项记录在 [来源清单](../scripts/benchmarks/jev_reference/README.md)，并用 Git blob/AST 核对。上游页面观测本来就限制可见文本 6000 字符、250 个控件动作和近期历史，两组共用这些限制；额外的 Laya 状态、指令、候选裁剪会在推理前被拒绝并记录，不能谎称模型看到了被裁掉的信息。

**加速是待检验假设，不是保证。** 多个决策头、候选构造、文本生成、失效恢复和工具等待全部计时，不把这些成本藏起来。

## 5. 任务与公平性

- 本轮只完成实现对齐，不擅自指定新的正式 benchmark。公开 Jev 的 Flights 演示及其少量重复不能作为泛化速度/质量证据，也不能代表 Laya。
- 本地 HTML 页面仅验证协议和浏览器执行，不是研究任务集。离线测试中的模拟模型响应只是测试替身，禁止将测试通过率、耗时或人为安排的调用数作为模型实验结果。
- 后续开发与正式任务必须分离；需要公开来源、冻结版本、可复位的相同初始状态和独立完成条件。任务集、数量、重复次数及质量容忍度仍待确认，不按 Laya 是否成功来选题。
- 当前接入使用独立 Chromium 上下文，不连接用户 Chrome 配置，不共享登录、cookie 或本地存储；限定网络源，禁用下载、弹窗页及服务 worker。这里只支持能由新上下文恢复初态的任务，服务器持久状态的复位必须另有经核查的基准适配，不能冒充已解决。
- 任务文件由可信研究者提供：`id`、`goal`、`url`、`allowed_origins`、`reset_policy`、`acceptance`。仅 goal 和实际观测进入模型；acceptance 的精确 URL、可见文本和字段条件只交给终末检查器。空验收被拒绝。
- 同题同重复轮次配对、串行执行，按固定种子排列 A/B 顺序；每次独立准备环境。重复次数不是独立任务数；正式实验须另确认均衡顺序设计，当前开发随机顺序不保证小样本完全均衡。
- 两组动作/时间预算、工具权限与重试政策相同。当前模型请求不自动重试、不根据未校准置信度回退到 Qwen；未来改变策略须先批准并冻结。
- 旧 AppWorld 接法不再作为当前任务链路，撤回原因及失败审计见第 8.4 节。

## 6. 必须记录的量化数据

| 指标 | 口径 |
| --- | --- |
| 任务通过率（主要质量指标） | 最终产物通过全部必需独立验收的尝试数 / 全部正式任务尝试；失败、超时、预算耗尽均计入分母。不是模型自报成功，也不是单个测试用例通过率 |
| 端到端耗时 | 工作区就绪且任务开始后，到最终验收结束；包含首次规划、候选生成、决策、工具、重规划、重试与恢复，不只计 D 的响应时间 |
| 耗时分布 | 两组全部尝试的均值、中位数、p95；另列成功与失败耗时，不能把提前放弃算作有效提速 |
| 成功配对加速比 | 双方均成功配对中，A 的平均耗时 / B 的平均耗时；同时报告配对数量，不能只给筛选后的速度而隐藏失败 |
| 模型调用 | 按 L-生成、L-决策、L-生成与决策混合、D-决策记录互斥用途标签；同一混合请求只计一次。记录实际调用数、决策问题数、逐次及累计耗时、token、错误和重试；本地批量大小及实际前向次数另记 |
| 工具与框架 | 工具逐次及累计耗时、次数、失败；候选构造、状态整理与验收开销单列，避免漏算 |
| 分工是否成立 | B 中实际由 D 承担的决策次数、L 请求总数及生成次数变化、重规划和回退次数 |
| 质量细分 | 每题结果、两组独有失败、错误恢复、破坏既有内容、提前结束；模型说完成不等于验收通过 |

### 6.1 三个主指标及计算口径

以相同任务、相同重复轮次构成一个配对；`N` 为独立任务数，`r` 为每题重复次数，每组尝试数 `n = N * r`。报告时同时写出这三个数，不能把重复次数当成样本多样性。

1. **任务通过率：** `p_A = A通过数 / n`，`p_B = B通过数 / n`；差值为 `100 * (p_B - p_A)` 个百分点。正式尝试中的模型、工具、基础设施错误和超时保留在分母并分项说明。中断造成未执行的登记任务也须列出；不完整实验不冒充完整配对结果。
2. **用时：** 报告两组全部尝试的均值、中位数与 p95，另列成功及失败分布。主要有效提速指标为双方均成功的配对集合 `P` 上 `S = sum(T_A[P]) / sum(T_B[P])`；`S > 1` 才表示该成功子集提速，同时公布 `|P| / n`。集合为空则记为不适用。不能只凭 B 提前失败导致的全体平均用时较短就宣布提速。
3. **大模型调用减少率：** 每次尝试记录 `N_L = N_L生成 + N_L决策 + N_L混合`，同一实际请求只能属于一个用途类别；在全部完整配对尝试上计算 `R_L = 1 - sum(N_L,B) / sum(N_L,A)`，分母为零则记为不适用。另列每任务调用均值、Laya 调用数、工具调用数及总模型调用数。即使总调用数增加，也可能出现大模型调用与总耗时下降；是否成立须实测，不能只用总次数判断收益。该指标也与成功配对口径并列展示，避免失败提前退出造成虚假的调用节省。

补充质量与成本核对：

- 列出“双方通过、仅 A 通过、仅 B 通过、双方失败”的配对计数，以及对应任务 ID、重复轮次和失败原因，直接回答两组是否在同一批任务上失败。
- 报告 `全部尝试累计端到端耗时 / 通过数`，表示失败成本也计入后的每个成功任务摊销耗时；通过数为零记为不适用。它不替代通过率，也不等同于并发吞吐量。
- 单次选择样例仅用于诊断，接口合法、模型速度快均不代表选择正确；不把接入冒烟检查换算成任务通过率。
- 每个测试用例通过率、token 用量、峰值显存和错误恢复次数仅作辅助。不同模型的 token 不直接视为等价成本；需要金额时按实际账单或已核实费率分别计算，不虚构本地推理价格。
- 小规模试跑的 p95 和差值仅作描述，不用于质量等价判断。正式实验的差值及加速比报告 95% 置信区间，按独立任务成组保留全部重复和 A/B 配对进行重采样；具体方法与正式任务量在运行前冻结。

### 6.2 计时与调用事件

用单调时钟记录任务及调用的开始、结束和持续时间；本地 Laya 的调用耗时覆盖输入预处理、推理和输出解析。GPU 计时须等待计算完成，不能只量异步提交时间；纯 GPU kernel 时间只能另作辅助。远程 L 请求从发起到完整响应或错误结束，网络等待保留。

每个逻辑请求有独立 ID，每次实际尝试有子 ID 和重试序号。例如一次失败后重试成功，逻辑请求为 1 次，实际调用为 2 次；SDK 自动重试和应用层重试均不能漏记。最终汇总以实际尝试为调用次数，回退到 L 的调用按实际职责归入生成、决策或混合，并额外标记回退原因，不能重复加总。异常路径也必须写出结束事件；未返回的 token 用量记为未知，不能填零。

每个记录须能关联运行、任务、重复轮次、实验组、请求用途和产物。保留脱敏后的状态、候选及来源、选择和工具结果以供核对；不得记录密钥。

模型加载、预热、工作区准备、清理与结果落盘另计，并给出整场运行总时间。若任务中触发加载或联网等待，必须留在端到端耗时内。阶段并行时同时记录实际墙钟时间与阶段耗时，不能简单相加后当作总耗时。

记录操作系统、CPU/GPU/内存、推理服务及模型版本、精度、上下文设置、思考配置、网络端点类别、并发、运行顺序和代码/任务集版本。服务端未知条件标为未知；部署差异不能全部归因于模型架构。

### 6.3 报告首页最少展示什么

首页只放一张 A/B 对照表：任务通过数/尝试数、通过率及百分点差、全部尝试耗时中位数/p95、双方成功配对加速比及覆盖数、每任务大模型总调用数与生成/决策/混合明细、Laya 调用数、重试数，以及两组独有失败数。后附逐题配对结果和环境条件；不能把关键质量差异藏进原始日志。

## 7. 如何解释结果

主要回答两个问题：B 是否更快；B 相对 A 的任务通过率变化是多少。先报告全部任务的质量与耗时，再报告双方成功配对的加速；调用次数及阶段耗时用于解释变化原因。

- 准确率差值按 B 减 A 报告，并报告不确定性；重复数据以独立任务为单位分组分析，不能把同题多次运行当作独立样本放大证据。
- “质量可接受的下降幅度”、正式任务量、重复次数与统计方法必须在正式运行前确认。未预设质量容忍度或证据不足时，只描述观测差异，不宣称质量等价。
- 即使 D 单次判断更快，若额外生成或恢复使任务整体变慢，也须报告协作方案未提速。
- 不预设加速倍数、目标延迟或成功结论；失败和负结果同样保留。
- 结果明确署名为“大模型生成 + Laya 决策”协作实验，并注明 checkpoint；只能支持本配置下的分工效果，不能作为 Jev 原版结果或所有决策模型均有效的证据。
